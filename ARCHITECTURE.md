# BugForge — Architecture Reference

## System Overview

BugForge is a full-stack web application that orchestrates AI-driven chaos engineering experiments against Docker Compose environments.

```
User Browser
    │ HTTP
    ▼
Next.js Frontend (port 3000)
    │ REST /api/*
    ▼
FastAPI Backend (port 8000)
    ├── /api/architectures     Architecture CRUD
    ├── /api/scenarios         LLM generation + approval
    └── /api/runs              Run lifecycle + observability + reports
         │
         ├── LLM Service ──────────────── IBM watsonx / OpenAI
         ├── Fault Engine ─────────────── Docker SDK → containers
         ├── Observability Collector ──── Docker logs + stats → PostgreSQL
         └── Report Service ───────────── Aggregates DB → report JSON
                               │
                          PostgreSQL (port 5432)
                               │
                          Docker Socket (/var/run/docker.sock)
                               │
                          Target Containers (Docker Compose)
```

## Data Model

```
Architecture
  └─< Scenario (many per architecture)
        └─< Run (many per scenario)
              └─< RunStep (ordered fault steps)
                    └── StepResult (pass/fail + notes)
              └─< LogEntry (container log lines)
              └─< MetricSample (cpu_pct, mem_mb per 2s)
```

### Key fields

- `Scenario.steps_json` — JSON array of `FaultStep` objects generated by the LLM
- `RunStep.parameters_json` — fault-specific parameters (delay_ms, memory_mb, etc.)
- `Run.status` — `pending | running | completed | failed`
- `StepResult.passed` — determined by absence of error-level log lines

## Data Flow

### Scenario Generation
1. User submits architecture form → `POST /api/architectures`
2. Frontend calls `POST /api/scenarios/generate`
3. Backend reconstructs architecture schema, calls `llm_service.generate_scenarios()`
4. LLM returns JSON array of scenarios; backend validates with Pydantic, persists as `draft`
5. Frontend displays scenarios; user approves or rejects each

### Run Execution
1. User clicks Launch → `POST /api/runs`
2. Backend creates `Run` + `RunStep` records, enqueues `execute_run()` as `BackgroundTask`
3. `run_executor.py` iterates steps:
   - Starts async log + metric collectors (threads via `asyncio.to_thread`)
   - Calls `fault_engine.apply_fault()` via Docker SDK
   - Waits `duration_seconds`
   - Stops collectors, calls `fault_engine.revert_fault()`
   - Writes `StepResult` (pass if no error-level logs)
4. Frontend polls `GET /api/runs/{id}` every 3 seconds; stops when terminal

### Report
1. After run completes, `GET /api/runs/{id}/report`
2. `report_service.build_report()` aggregates steps, metrics, and logs
3. Computes: peak CPU, peak memory, error log count, pass/fail per step
4. Optionally calls LLM for narrative summary (if `LLM_REPORT_NARRATIVE=true`)

## Fault Injection Details

All faults target Docker containers by partial name match against the `target_service` field.

| Fault | Docker Operation | Revert |
|---|---|---|
| `kill_container` | `container.kill()` | `container.start()` |
| `pause_container` | `container.pause()` | `container.unpause()` |
| `network_partition` | `network.disconnect(container)` | `network.connect(container)` |
| `cpu_stress` | `docker exec stress-ng --cpu` | `pkill stress-ng` |
| `memory_stress` | `docker exec stress-ng --vm` | `pkill stress-ng` |
| `inject_latency` | `docker exec tc qdisc add netem` | `docker exec tc qdisc del` |

> `inject_latency` requires `iproute2` in the target container image.
> `cpu_stress` and `memory_stress` require `stress-ng`.

## LLM Prompt Design

The system prompt instructs the LLM to output a strict JSON array. Key constraints enforced:
- Each scenario has 2–4 steps targeting **different** services
- Scenarios must be compound and non-obvious (the main value proposition)
- Fault types are restricted to the implemented set
- Parameters follow a defined per-fault schema
- Malformed responses trigger one automatic retry, then a 502 error

## Extension Guide

### Adding a new fault type
1. Add the enum value to `FaultType` in `fault_engine.py`
2. Add `apply_fault` and `revert_fault` branches
3. Add the fault type description to `SYSTEM_PROMPT` in `llm_service.py`
4. Add a color mapping in `frontend/src/components/ScenarioCard.tsx`

### Switching LLM providers
Set `LLM_PROVIDER=watsonx` and provide `WATSONX_PROJECT_ID` + `LLM_API_KEY` + `LLM_MODEL`.
Both paths share the same prompt and output contract.

### Upgrading to async job queue
Replace `BackgroundTasks` with Celery + Redis:
- Move `execute_run` call to a Celery task
- Add `CELERY_BROKER_URL` to config
- No other code changes needed (executor is already async-idiomatic)
